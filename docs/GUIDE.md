## 她是怎么工作的

三条**严格互斥**的路径：

| 路径 | 触发 | 谁说话 | 做什么 |
| --- | --- | --- | --- |
| **接管回复**（默认） | 消息走到大模型那一刻（被 @、或意图路由放行） | 本插件自己 | 自己调大模型拿到 `reasoning` + `actions`，执行动作并发送，然后 `stop_event()` 阻止主人格重复回复；她说不出话或模型出错时自动交回主人格 |
| **注入状态**（可选 / 兜底） | 同上，或接管失败时 | AstrBot 主人格 | 只往 `system_prompt` 追加「她此刻在书房、很困、想起上次在这里说过的话」，并按区域裁剪可用工具 |
| **自主行为** | 日程到点、决策器判定、插话、工具动作的后续 | 本插件自己 | 走动、发呆、看书、做饭、搜索、主动搭话 |

如果消息根本没走到大模型（被别的插件用表情包回掉了、命中了指令等），本插件完全不介入。
三条路径互斥，所以不会出现"一次 @ 回两条消息"。

## 两张地图：世界与区域

地图分两层，**区域本身也是一个节点**：

| 层 | 画的是什么 | 怎么进 |
| --- | --- | --- |
| **世界地图** | 一个个区域节点（家中、街心公园…）和区域之间的连线 | 打开「地图」页默认就是它；点区域进入，或双击区域节点 |
| **区域地图** | 这个区域里的地点（卧室、阳台、书房…）和它们之间的路 | 左上角「← 世界地图」返回 |

两层用的是**两套坐标**：区域节点在世界地图上的位置，和区域里地点的位置互不相干——
在世界地图上拖动区域，不会影响区域里地点的排布。

**跨区连线是「门户对」**：每条线两端各自指定一个地点。比如公园有北门和南门，
「公园 ↔ 商场」这条连北门 ↔ 商场大门，「公园 ↔ 学校」连南门 ↔ 学校门口。
同一对区域可以有多条这样的线，她走的时候会自动挑最省的那条。
寻路上其实是一张图（地点 + 区域内的路 + 跨区的门户），所以"从卧室去公园的鸽子广场"
会算成"走到大厅 → 跨区 → 从北门走到广场"的总 tick，提示词里直接给这个总数，她只写一次 `walk_to`。

## 一张地图，多个会话

这里容易搞混，先讲清楚：

| 东西 | 范围 |
| --- | --- |
| **地图、节点、连线、动作、日程、全局设置** | **全局共享一份**（`world.json` / `schedules.json`） |
| **她的位置、五个数值、心情、当前动作、计划、场景记忆** | **每个会话一份**（`state.db` 里的 `WorldState`） |

也就是说：所有群共用同一张地图定义，但"她在 A 群睡觉、同时在 B 群做饭"是成立的——位置和状态
互不影响。记忆也是按「会话 + 人格 + 地点 + 人」分开存的，不会串群。

编辑器地图页为此提供了两个东西：

- **查看会话**下拉：选择看哪个会话的位置（选中的那个会显示高亮边框 +「她在这里」）；
- **显示所有会话**勾选框：把她每个会话的位置同时标在地图上，非当前会话用虚线和会话短名标注，
  鼠标悬停可以看到完整列表。地图页每 10 秒自动刷新一次位置。

「会话」管理页也会显示每个会话此刻在哪个地点、什么状态。

## 网页编辑器

插件在 AstrBot WebUI 的插件详情页里提供「**虚拟世界编辑器**」：

- **实时状态**：左栏分三小节——**时间与日程**（现在几点/什么时段、世界时间对照、下一条日程还有多久）、
  **正在进行**（当前动作进度条、计划进度、区域 · 地点、从这儿能走到哪）、
  **互动与运行**（最近活跃的人、没回的群聊条数、刚才在聊什么、决策意愿、本小时剩余额度、
  发送通道与模型通道状态：最近一次模型调用成功还是失败、发送失败后还剩多少秒冷却）；
  右侧是数值、当前计划（可读的步骤列表）、内心活动、最近一次推理草稿，下面是事件日志；
  数值平时是彩色的条（绿→黄→橙表示离「该注意」还有多远，精力这类越高越好的反过来算），
  点「编辑数值」才变成滑杆，**群名片可以直接填**（都有保存按钮，改动会记一条日志）；
  刚有动作被跳过时状态卡上会直接显示为什么；推进 tick / 触发决策 / 打断 / 叫醒 四个按钮都会给结果提示，
  她没在做事、没在睡觉时按钮会灰掉；「触发决策」是手动触发，不受评估间隔限制
- **地图**：分**世界地图**（区域 + 跨区连线）和**区域地图**（地点 + 区域内连线）两层，左上角面包屑来回切；
  单击区域/地点是选中编辑（会高亮），**双击区域直接进入区域地图**；
  拖动摆位置、连线中点标出走过去要几个 tick；跨区连线在区域属性里编辑（两端各选一个地点 + tick + 是否双向），
  区域地图上会把这些通道标成出口；可以按会话查看位置，也可以一次显示所有会话分别在哪；
  区域属性里能「用大模型生成地点」、地点属性里能「用大模型生成动作」，生成结果先列在弹窗里让你改、勾选，确认后才写进配置
- **动作库**：卡片网格，每张卡左上角是**启用开关**（停用 = 她根本没有这个动作），右下角三个图标
  是复制 / 编辑 / 删除；点卡片从右侧滑出**编辑抽屉**（带保存键），按动作类型自动隐藏无关字段；
  分组可以自己写（下拉里是已有分组，也能填新的）、地点是多选、工具可以多选
  （参数只读展示每个工具自带的定义）、完成效果是
  「属性 + 增加/减少/设为/乘以 + 数值」的行编辑，**不需要手写 JSON**；
  顶部还有搜索、分组筛选和「编辑 JSON」
- **日程**：星期是七个可选按钮，动作链按行编辑（选动作、选目标地点、填时长、填要说的话），触发条件同样是多选；
  动作下拉里会直接标出「（需先在书房）」这样的地点要求，缺移动时可以一键「↩ 先移动到X」，
  也可以打开日程的「自动先走过去」让插件自己补
- **会话**：白名单增删与启用/禁用、冷启动模式
- **记忆库**：按节点/类型/作用域筛选、统计；编辑与新增是**弹窗表单**
  （内容 / 类型 / 作用域 / 绑定地点 / 权重 / 情绪标签），删除与恢复默认都有确认框；
  每行可勾选，支持「全选 / 删除选中 / 清空本会话」
- **日志**：把她的每一次决定与动作按时间排成一条线——用户说了什么、她决定做什么（决策原因 / 模型原话 /
  推理草稿）、真正执行了什么、说了什么、哪些动作被跳过以及为什么。支持按会话、类型、关键词筛选，
  点任意一条可以看原始数据，也能勾选批量删除 / 清空本会话、一键导出 JSON
- **全局设置**：按「基础 / 她的初始状态 / 状态变化速度 / 说话频率与预算 / 说话节奏 /
  没人理她时怎么办 / 孤独感与插话 / 记忆 / 工具 / 上下文 / 图片转述 / 群名片 / 内容安全」
  分卡片，字段全中文命名，每项都有悬停说明；
  高级用户仍可在最底部直接编辑 world.json
- **调试**：预览注入内容与自主提示词、查看已注册工具、备份配置

编辑器默认复用 AstrBot WebUI 自身的登录鉴权。如果你把 WebUI 暴露在公网、想要二次保护，
可以在插件配置里填 `web_password`（或在编辑器里设置密码），之后编辑器会要求单独登录。

## 动作编辑里的每个概念

| 字段 | 含义 |
| --- | --- |
| **动作类型** | 瞬时=立刻完成（说话、抱抱）；持续=占用一段时间（睡觉、看书、上网） |
| **执行层级** | 模板=不调大模型，直接发固定文案（最省钱）；单轮=让大模型说一句（日程 / 计划里的步骤没有现成台词时也会现场生成一句，没模型或额度用完才退回动作文案）；工具型=调用 AstrBot 里已注册的工具 |
| **生效范围** | 全局=任何地点都能做；仅特定地点=只有站在指定地点时才存在这个动作 |
| **限定地点** | 配合「仅特定地点」使用：这个动作属于哪些地点。她不在那儿时它不会出现在她的选项里 |
| **分组** | 动作库里的归类。留空按用途自动归类；也能自己起名字（下拉里是已有分组，可以直接填新的） |
| **启用 / 停用** | 停用等于"根本没有这个动作"：不进场景动作表、不进提示词、绑定的工具也不再算、计划里排到就跳过；她正在做的那次会立刻停下 |
| **目标** | 自己/空间、某个群友、整个群。指向人的动作会以动作描述发到群里 |
| **持续时间** | 「固定时长」每次一样；「由大模型决定」把时长交给模型在**最短~最长**之间自己定（例如小睡睡多久），超出区间自动夹住 |
| **执行期间状态标识** | 执行中她的状态（sleeping / reading…），会影响群名片文案与状态判断 |
| **完成时一次性效果** | 做完立刻生效一次，例如「心潮 增加 0.28」；「设为」会直接覆盖当前值 |
| **每持续 1 分钟的效果** | 按实际持续时间累加：小睡写「精力 增加 0.0015」，模型决定睡 30 分钟就 +0.045，睡 60 分钟就 +0.09 |
| **完成后** | 什么都不做 / 让她接着说一句（把结果讲成人话）/ 接着执行另一个日程 |
| **使用的工具** | 只有「工具型」动作才有：至少选一个 AstrBot 里真实注册的工具，也可以选多个（按顺序依次调用）。工具的参数不用你填，运行时由辅助模型按每个工具自己的定义补全 |
| **固定参数** | 工具型动作才有：填过的参数每次都用你写的值，不再交给模型猜。主要用来兜底「工具把参数写成可选、实现却必须要」的第三方工具（例如查天气固定 `city=武汉`） |
| **内置** | 引擎对它有专门逻辑（说话 / 移动 / 睡觉 / 想事情 / 分享 / 回想 / 戳一戳 / 日程三件套），**只能停用、不能删除**；误删会按默认值自动补回 |

**动作归属只有一份数据。** 地点页面里的「可用动作」和动作里的「限定地点」是同一个字段的两个视图：
在地点里勾上一个动作，动作的限定地点里就会多出这个地点；反过来也一样。全局动作在任何地点都能做，
所以在地点页面里它以「通用动作」只读列出，要改范围就去动作库改。

## 用大模型批量生成

两个生成入口（用的是插件配置里的「**内容生成模型**」，运行时完全不调用）：

| 入口 | 生成什么 | 上限 |
| --- | --- | --- |
| 生成地点 | 给这个区域添几个地点（名称 / 描述 / 氛围 / 图标 / 颜色） | 一次默认 3、最多 5 |
| 生成动作（在**地点属性**里） | 照着这个地点（以及它所属的区域）写几条能做、又值得在群里讲一句的动作 | 一次默认 3、最多 5 |
| 批量生成动作（在**区域属性**里） | 给这个区域里的**每个地点各**生成几条动作，走同一套弹窗勾选 | 每个地点默认 3、最多 5 |

生成结果**不会直接落库**：会先弹出一个列表，每条都能改名字、改归属地点、删掉，还可以只勾其中几个；
点「确认加入选中的」会**直接保存并生效**（不用再点右上角「保存」）。

- 生成动作时会带上：区域名与说明、这个地点的 id/名称/描述/氛围、人设、已有动作（防重复）、
  当前注册的工具名。生成的动作默认绑到它所属的地点，同名 id 会自动加后缀；
  模型要是写了不存在的工具，会被剔掉并在列表下方提示；一个都不剩时降级成"让她自己说"。
- 生成地点时会自动摆位（接在已有的地点旁边，不会重叠），并按**方案 A** 连线：
  第一个新地点连到区域内最近的一个既有地点，之后依次串成链，默认 1 tick（都在预览里可见、可改）。

## 工具是怎么被调用的

**参数补全什么时候触发**：只要工具声明了参数、而这次没给全，就会让辅助模型补一次
（不只是"缺必填"时）。如果调用时报「缺少参数 / 参数不匹配」这类错，插件会带着报错再补一次并**重试一次**，
所以「schema 里写着可选、代码里其实必须要」的第三方工具也能跑通。
每个工具的原始必填列表可以在「调试」页看到。

**参数不需要你手写，也不需要主模型一次写全。** 调用分两步：

1. 她（主模型）只输出**意图**——「查一下今天有什么科技新闻」，用自然语言说清想干什么；
2. 插件拿这个意图 + 工具自己的参数定义（名称、类型、说明、是否必填），
   交给**辅助模型**（插件配置里的 `helper_provider_id`）翻译成参数字典，再用 schema 校验一次，最后真正调用工具。

这样主提示词不用塞进所有工具的 schema（否则又长又不准），填参数时模型也只需要盯住一个工具。
同一个「工具 + 意图」会命中缓存；每小时有次数上限（全局设置 → 说话频率与预算 → 每小时最多补全工具参数次数）。

你要做的只是**在动作里选好「用哪个工具」**——工具只挂在动作上，不再需要在节点里配一遍。
没选工具的工具型动作会被跳过，日志里会写明原因；选了但 AstrBot 里没注册，同样跳过。
工具结果默认会交回主模型，让她用自己的话说出来（可在「全局设置 → 工具」里关掉）。

**结果里的图片也认得出来**：工具或指令返回 `event.image_result(...)` 这类带图的消息时，
插件会把图单独挑出来——配了转述模型就先转述成文字，没配就直接交给多模态主模型一起看，
返回文字则按组件还原（文本、`@某人`），不会把一串 `MessageEventResult(chain=[...])` 的对象表示丢给模型。
「指令触发」型动作和工具型动作走同一套规则：动作里的「完成后」与全局的「工具结果回话」都关掉时，
执行完就安静，不会再强行说一句。

**一个动作可以挂多个工具**，用「工具用法」决定它们怎么配合：

| 用法 | 行为 | 什么时候用 |
| --- | --- | --- |
| 按顺序都调（默认） | 装了的都调一遍，结果合并 | 确实要串起来，例如先搜索、再抓正文 |
| 依次尝试 | 只用一个：按顺序挑第一个能用的，失败换下一个 | 同一个意思装了好几个工具，互为备份 |
| 智能选择 | 让辅助模型按她的意图挑一个（挑工具与补参数一次完成） | 工具用途差别大，靠名字分不清该用哪个 |

选择器按来源分组（官方 · 搜索 / 官方 · 其它 / 插件 · 具体插件名），可以搜索、
**用下拉只看某一组**、折叠、全选本组。后一个工具补参数时，会把前一个工具查到的内容一起给补全模型，
所以「先搜网址、再抓正文」这种链条不用你手填参数；中间哪个工具缺必填参数，只会跳过它自己并写进日志。
工具越多每一步越慢、也越容易失败，只在确实需要配合时才挂多个。

**工具坏了会被临时停用**：同一个工具连续两次「调用不出去」（没注册 handler、报错、超时、连接断开）
就进入退避——30 秒起、每次翻倍、最长 30 分钟，期间不再尝试它。参数写错、结果为空不算坏，不会触发。
退避到期自动放行试探一次，成功就清零；改配置（重载）会全部解除，
「实时状态 → 互动与运行」里也能看到被停用的工具与剩余时间，点「重试」立刻解除。

内置的「上网搜索」「查天气」**不带任何默认工具**——工具要你自己在动作里挑。
没挑（或挑了 AstrBot 里没有的）时这一步会被跳过，日志与编辑器横幅里会写明是哪个动作缺工具。

哪一类工具会出现在提示词里？只有「全局设置 → 工具 → 通用工具」里勾选的那些
（任何地点都能调用）；地点专属的工具不用单独配——把它绑到那个地点的动作上就行。

「按地点裁剪 AstrBot 工具集」也是按这个推导：主人格在她当前地点能用的工具
= 通用工具 + 当前地点可用动作绑定的工具。

**工具写法兼容**：AstrBot 里的工具有三种实现方式——`@filter.llm_tool` 的 `handler`、
新版工具的 `call()`（MCP 工具、很多第三方插件都是这种）、以及老的 `run()`。
插件按同样的优先级依次尝试，所以「没有可调用的 handler」这种报错只会出现在
三种入口都没有的坏工具上。返回 MCP 风格的 `CallToolResult` 时也会把里面的文本取出来，
而不是把整个对象塞给模型。

**官方内置工具也在列表里**：编辑器里带「官方 ·」前缀的就是 AstrBot 自带的内置工具
（`web_search_tavily` / `web_search_bocha` / `web_search_brave` / `web_search_baidu` /
`web_search_firecrawl` / `web_search_exa` / `web_search_anysearch`、配套的网页正文抓取、
知识库检索、定时任务、电脑操作等）。它们不在 AstrBot 的插件工具列表里，是单独存放的，
插件把它们一起列了出来，所以不用为了搜索再装一个第三方插件——**直接把 AstrBot 里已经配好的
联网搜索绑到动作上**就行（工具的说明里带自己的参数定义，参数依旧由辅助模型补全）。

注意：`send_message_to_user` 这类「直接发消息」的工具会被标成不可用——它绕过本插件的回复管线
（发送前插件、表情包识别、分段回复都会失效），所以不参与动作；没配 key 或没启用的官方工具
调用会失败并写进日志，不会让流程卡住。

### 联网检索

工具型动作有一个「调用形态」。默认的「直接调用」是把工具结果原样交回给她；
选「**联网检索**」就走一条查资料专用的流水线，适合「上网搜索」这类动作：

1. **她要查什么**：动作里写 intent 就行；要分角度查时还能一次给 1~3 条 `queries`
   （例如「今日热点新闻」和「某某事件 最新进展」）。她只写了意图、没给查询词时，
   由辅助模型把意图翻成一条能直接丢进搜索框的查询词。
2. **结果整理成证据**：搜索工具返回的 JSON、一行行带链接的文本、或者一大段散文，
   都会被归一化成带编号的条目（标题、链接、摘要、时间），去重后最多留 8 条——
   她能对着编号讲，日志里也看得出「这句话是照哪条说的」。原文永远完整留在日志与工具结果里，不截断。
3. **读正文（可选）**：在「阅读网页工具」里选上能把网址换成正文的工具后，
   插件会挑结果里最靠前的几篇抓正文（每篇最多 1200 字，同一篇 6 小时内不重复抓）。
4. **不够就补查**：证据太少时，让辅助模型换个角度再给一两条查询词，按「检索深度」决定补几轮。
5. **她照着证据讲**：提示词里只有证据块，规则是「证据里没有就直说没查到、不许编数字和时间、
   别照抄原文、别念网址」。整条流水线（多条查询 + 读正文 + 补查）最多花 20 秒，超时就用手上已有的证据。

「检索深度」三档：**快查**只查一轮、不读正文也不补查；**标准**（默认）读前两篇、最多补查一轮；
**深挖**至少读三篇、最多补查两轮。

自定义动作也能用这个形态：把「搜索主题」写清楚（例如「今日新闻热点」），
或者用「查询模板」套格式（`{date} 新闻热点`、`{topic} 最新消息`）。
优先级是：她写的意图（含日程里写的那句）> 搜索主题 > 查询模板 >
**让她自己想一句**（规则触发时问一句"你现在想查什么"，带上她此刻的位置/状态和群里最近聊的事）>
中性兜底主题（「今天有什么新鲜事」）。

**规则触发也能有像样的意图**：好奇心、日程这类不是大模型安排的检索，本来没有"她自己的意图"，
现在会按上面的顺序补上——配了主题就用主题，没配就让她照着当下处境和群聊话题自己想一句
（这一步算在「每小时最多自主发言文案」的额度里，没额度/没模型时才退到中性主题）。
配了主题的好处是稳定、还省一次调用；不配的好处是话题会跟着群里正在聊的事走。

**为什么兜底不用动作说明**：说明写的是"这个动作怎么用"（例如「上网查东西（在书房用电脑）」），
拿它当"要查什么"，补参模型只能自己编一个"全球新闻 + 天气 + 比分"式的万能查询，
搜出来全是聚合站和应用商店。规则触发（好奇心、日程）时没有她自己的意图，
所以这类动作**建议配一个搜索主题**；不配也不会再退化成那种万能查询。
另外生成查询词时会额外要求：关键词 20 字以内、只查一件事、不要写成「获取……的最新信息」这种句子。

**来源去哪了**：默认只写进日志与调试输出（`🔗 检索来源`，调试输出里默认不勾选，不会发到群里）；
想让她的回复末尾带一条参考链接，就把「讲结果时带来源」打开。

### 一次检索是怎么收敛的

检索不是"她说一句、查一次"，而是一段**在插件内部跑完**的流水线（学网页版那套做法）：

1. **谁来决定查什么**：她自己写的意图 → 动作里配的「搜索主题」→ 查询模板 →
   让她按当下的处境和群里的话题自己想一句 → 中性兜底（「今天有什么新鲜事」）。
2. **她可以说要查多深**：动作输出里可以写 `queries`（几条查询）、
   `search_depth`（quick / standard / deep）和 `read_pages`（读几篇）。
   **动作里配的是上限**——她只能往浅里调，不能超过配置。
3. **查完先压成要点**：读回来的正文由打杂模型整理成「结论 + 编号要点」再交给她，
   而不是把一堆原文丢过去（材料本来就很少很短时跳过这一步，不浪费调用）。
4. **够了就停**：证据够用（至少两条、其中一条有像样的正文）就不再补查；
   补查一轮之后如果一条新东西都没多出来，也直接停——不会为了一个查不到的词反复换词搜。
5. **刚查完这一轮不再接检索**：续说那一轮她想再写一次搜索也会被拦下（日志里记一条「续说这一轮不再接…」），
   只剩"说话"。动作链条太深时，工具 / 指令型动作同样会被拦下。
6. **上一轮查过什么会带进下一轮提示词**（一小时内的检索会写成一段「最近查过」），
   免得她隔一轮又用同样的词查一遍。

**回显合并**：一次检索里查了 3 条、读了 2 篇，群里只会看到两三行——
`🔧 搜索 ×3：词1 / 词2 / 词3`、`📖 读正文 ×2`、`📥 共 7 条可用结果`；
细节仍然完整留在「日志」页。打开「精简模式」时只留 `🔧 搜索 ×3` 这一行。

**挂了多个搜索工具**：检索形态下只有**第一个能用的**会被当成搜索入口；
它要是坏了（没有 handler、超时、连接断开…），插件会把剩下的候选取来接着查同一条查询。
要抓正文请在下面的「阅读网页工具」里单独配。

## 她看得到什么

每次组提示词时都会带上这些，越靠前越重要：

| 内容 | 说明 |
| --- | --- |
| **现在的日期时间** | 运行时状态的第一行：`现在是：2026-09-12（周六）23:40 —— 深夜`。没有它，模型分不清"深夜该去睡"和"白天犯困才小睡" |
| 当前场景 | 在哪、氛围、这里能做什么、**从这里出发去每个地方要几 tick**（含 id，按距离排序，走不过去的会标出来） |
| 状态数值 | 每个值都带 0~1 的范围和高低两端的含义，心潮还会给一句程度描述 |
| 手头的事 | 正在做什么（还剩几 tick）、计划里还没做的（带这份计划的原因）；手头空着时补一句「你上一次安排好的是：…」，免得每轮从零重想 |
| 内心活动 | 最近一次推理草稿（在哪 / 状态 / 心情 / 在和谁说话 / 打算怎么办） |
| 记忆 | 这个地点、这个人相关的场景记忆，**每条带日期和时段**（`[09-11 晚上] 她说想换工作`），并且按时间从早到晚排——越靠下越新 |
| 群聊上下文 | 一条按时间排的对话流：别人的话带昵称和 id，她自己的话标成「你:」；合并转发会注明。她说出去的话都算——被 @ 的接管回复和主动发言都会记下来，下一轮不会被要求重复同一个句式 |
| 是不是在对她说 | 被 @、私聊、叫了她的名字、或者紧接着她那句话往下说 → 按「对你说」处理；其余一律按「群里在聊，她去插一句」处理，提示词会写明「没有人点名找你」，免得她把别人的闲聊当成对自己的请求 |
| 说话密度 | 最近一段时间她说的句数超过阈值时，会多一段提醒：「这轮尽量少说话，能只做动作就别开口」 |
| 图片 | 配了 `vision_provider_id` 时：先转述成文字（提示词可在「全局设置 → 图片转述」里改，默认会认出是不是表情包 / 什么梗；描述也会写进聊天留档，后续轮次仍看得到）；没配时：**直接把图片交给多模态主模型**（自上次回复以来最多「一次最多带几张图」张，含引用消息里的图）。取图走 AstrBot 自己的组件解析，http / 本地文件 / base64 都支持；**取不到地址也会写一条日志**（附协议端给的字段），成功与失败都能在日志里「图片内容」看到 |

**想看完整提示词**：编辑器「调试 → 预览注入内容 / 预览自主提示词」里会给一份**分段索引**
（每段标题 + 字符数）再加上全文——提示词三四千字，索引能让你一眼确认"某一段到底进去没有"。
群里用 `/vw debug autoprompt` 只会回索引和文件路径（完整内容写到
`data/plugin_data/astrbot_plugin_virtual_world/prompt_autonomous.txt`），
因为把几千字直接丢进聊天窗口会被平台截掉尾巴，正好是「群里最近在聊」「你最近说过的话」那几段。

## 群聊上下文怎么存、怎么带

「保存下来」和「带进提示词」是两件事，配置也分开：

| 层 | 在哪配 | 默认 | 说明 |
| --- | --- | --- | --- |
| 留档 | 全局设置 → 上下文 → 留档保留多少条 | 200 | 存在 `state.db` 里，重启后还在；只按条数滚动 |
| 携带 | 全局设置 → 上下文 → 最多携带多少条聊天 / 多久内算「还热乎」 | 12 条 / 20 分钟 | 每轮提示词里带的那一小份 |

留档超出上限时有两种处理：

- **直接丢弃最早的**（默认）：不额外调用模型，最省；
- **压成摘要**：把较早的聊天交给 `context_provider_id` 压成一段摘要，
  摘要会一直跟着提示词，原文只留最近的若干条。压缩在 tick 里发生，
  有「攒到多少条开始压」「压缩后保留多少条原文」「两次压缩至少间隔多久」三个参数控制频率。

调试时可以在「实时状态」页直接点 **清空上下文**：它会清掉这个会话的留档与摘要，
世界状态、记忆、日程都不受影响；旁边还有「群聊上下文」面板可以确认当前留档条数和摘要原文。

### 提示词里的群聊分三段

她看到的群聊背景不是一大坨，而是按"有没有回应过"分开的三块：

| 段 | 内容 | 为什么要分 |
| --- | --- | --- |
| 之前的群聊 | 她上一轮已经回应过的那批，压成一条概览（谁说了什么、她回了什么）+ 更早的压缩摘要 | 这些再回应一次就重复了；但直接删掉她就会失忆 |
| 最近在聊什么 | **她还没回应过**的原文，带时间（`[21:04] 小明(42): …`）；同一个人连着说的几句合并成一行；图片的转述描述跟着消息一起带进来 | 这才是这一轮真正要接的内容 |
| 你最近说过的话 | 她最近 3 条发出去的话 | 提示她别再用同样的开头和句式 |

「已回应水位线」是在**她真的开口之后**才推进的：推进时把她刚刚回应过的那批压成概览，
水位线之后的消息才算"还没回应过"。判断用的是**序号**而不是时间戳——
时间戳只精确到秒，她说完的同一秒里进来的消息会被误判成"已经回应过"。

@ 的记录也在这里：消息里 @ 了谁会被写成 `他(QQ号)`，@ 到她自己的会标成 `你（名字(QQ号)）`——
她并不知道自己的 QQ 号，不标出来就分不清那是不是在叫她。

图片转述会连同**当前消息、引用的消息、最近几句群聊**一起交给多模态模型，
输出「画面描述｜类型｜与话题的关系」，所以同一张图在不同话题下会得到不同的描述。
其中「类型」就是**表情包识别**：默认提示词要求它先判断这是不是表情包 / 梗图、是什么梗、什么情绪，
因为接一张梗图和接一张照片的方式完全不同。这段提示词在「全局设置 → 图片转述」里可以改，
留空就用内置默认；转述模型看不到群聊，所以要在提示词里把「描述里必须包含什么」交代清楚。

### 同一张图只识别一次

表情包、梗图在群里会反复出现，所以转述结果是**按图片指纹缓存**的（默认开，在「全局设置 → 图片转述」里可关）：

- 指纹来自图片内容本身：协议端给的 `base64` 直接对内容算摘要，http 链接只取路径——
  同一个文件换个带 token 的临时链接也能认出来；
- 缓存写在 `state.db` 里，**重启插件后仍然有效**；默认最多 500 张、保留 30 天，按最近使用淘汰；
- 命中时只复用「画面描述｜类型」这半句，**「与话题的关系」不会跟着复用**——
  换个话题发同一张表情包，关系由主模型看当前上下文自己判断，不会拿着上一轮的结论硬套；
- 识别失败**不写缓存**（偶发超时不该被永久记成"看不出"），60 秒内也不重复重试；
- 同一张图在两条消息里同时出现时，只会识别一次，第二条等第一条的结果。

省下多少次识别可以在同一块里看到（"已记住 N 张图，累计省下 M 次识别"）。

## 关于「直发消息」的工具

AstrBot 内置了 `send_message_to_user` 这类直接把消息发给当前会话的工具。
**本插件不会调用它们**——走这条路会绕过 AstrBot 的回复管线（发送前插件、表情包识别、
分段回复、合并转发都不会命中），还容易重复发言：

- 插件自己的动作解析工具时会跳过它们，自动匹配也绝不选中，日志里会写明原因；
- 编辑器的工具列表里它们带 ⚠ 提示；
- 主人格那条路径默认也是安全的：开启「按地点裁剪 AstrBot 工具集」时，
  她能用的工具是由"当前地点的动作绑定的工具"推导出来的，里面没有它们，等于已经被裁掉。只有你关掉裁剪、或把它勾进通用工具时，
  主模型才可能调用它们——那是 AstrBot 的原生行为。

模板文案支持三个占位符：`{bot}`（她自己）、`{user}`（动作目标群友）、`{node}`（当前地点），
例如 `（{bot}抱了你一下）`。

## 分段回复的节奏

她一次说了好几句时，是一段一条消息发的（而不是挤成一坨）。为了让这个过程看起来像人在打字，
两条之间会按上一段的字数停一下再发：默认 **0.03 秒/字、单条最多 2.5 秒**，
在「全局设置 → 说话节奏」里可以改，也可以整体关掉。

`{user}` 认不出人时不会把 QQ 号写进句子里（会退回「你」），日志里仍然记录了真实的目标 id。

## 日程动作链与移动

**地点是硬条件，不会被无视。** 「上网搜索」这类动作写了「要求她在书房」，
如果到点时她人还在卧室，这一步会被**跳过**（日志里记成一条 `skip`），
后面的步骤照常执行。这样设计是为了让她真的「走过去」而不是瞬移。

所以在日程里想让她「早上先去书房再查新闻」，有三种写法：

1. **打开日程的「自动先走过去」（推荐）**——动作链里只写 `上网搜索` 就行。
   到点时插件会看她在哪儿，自动在最前面补一步「移动到书房」（会挑最近的那个满足要求的地点），
   路上的耗时按地图上的连线 tick 数算。
2. **手动补一步**——在动作链里点那一步右边的「↩ 先移动到书房」，会帮你在它前面插一条「移动到」。
   适合你只想让某一步走过去、别的步骤保持原样。
3. **完全手动**——自己下拉选「移动到」，再选目标地点。

动作链里每一步的动作名是**点开的弹窗**（不再是下拉）：动作多了以后可以搜索、
按分组只看一类（官方工具、某个插件、内置动作…），和地点里选动作是同一个窗口。

两者可以混用：自动前往遇到你已经手写的「移动到」不会重复插步骤。
如果多个会话共用同一份日程，这些移动是**按会话各自算**的——她在 A 群的位置不影响 B 群。

新建的日程默认开启「自动先走过去」；默认自带的三个日程（早安、做饭、睡觉）也都是开启状态。
把它关掉，就回到「地点不对直接跳过」的老行为。

**不想等到点？用「立即执行」**：日程列表每行右侧（以及日程属性表单底部）都有一个
「▶ 立即执行」，会在你指定的会话里马上跑一遍这条动作链——忽略时间、星期和触发条件，
结果会真的发到群里。它**不占当天的触发名额**，到点之后这条日程照常还会正常触发。
群里也能用 `/vw schedule run <日程 id>`（管理员）。

**工具 / 指令型步骤要写「意图」**：这两个层级的动作靠一句「想干什么」去补参数，
动作链里忘了写就会被跳过（日志里是「没有给出想做什么」）。所以每步都有个意图输入框：

- 留空也没关系——保存时会用内容生成模型补一句写进配置（编辑器里能看到、能改），
  运行时再兜一句动作自己的说明；
- 想自己写就写清「这一步要它干什么」，例如「看看今天有什么科技新闻」，比自动生成的准。

**智能日程**：每条日程可以单独打开「智能日程」。开了之后，到点会把这条**动作链**交给大模型，
让它给工具 / 指令型步骤写一句「这一步想干什么」，再**照原样执行**——步数、动作 id、时长、
台词都不变，所以不会出现"配的是查热搜新闻、它却去上网搜索"这种事，也不用它操心怎么走路
（自动前往照旧由插件补）。所以动作链里的意图框会隐藏起来（不用填了）。

为了不给模型干扰，这次调用只带最少的信息：**她的人设**、现在几点、她在哪、什么状态，外加
**一句**话题背景（她自己写的那句「刚才在聊什么」，不是原始聊天记录）；她平时那套提示词
（可达表、工具清单、记忆、群聊、内心活动…）都不带。人设是为了让这句意图符合她的身份和口味，
但提示词里也写明了「这是给工具的明确交代，不要写成对群里说的话」。
代价是每次到点多一次主模型调用；模型没给出可用意图时会退回用你在意图框里写的那句、
或者动作说明兜底。想要"到点一定发生同一件事"就别开它。

## 模型用在哪里：两类便宜模型 + 主模型

插件会用到**几个**不同的模型来源，搞混了很容易出现"明明配了便宜模型，账单还是很高"：

| 来源 | 谁在用 |
| --- | --- |
| **插件配置里的 `llm_provider_id`**（插件用模型） | 插件自己发起的所有调用（见下表） |
| **插件配置里的 `vision_provider_id`**（看图模型，多模态） | 所有「把图变成文字」的活：群友发的图片转述、天气工具返回的天气图 |
| **插件配置里的 `helper_provider_id`**（打杂模型，文本） | 零碎活：补工具参数、压缩上下文、判断图和话题的关系、把天气结果整理成一行 |
| **插件配置里的 `creator_provider_id`**（内容生成模型） | 编辑器里「批量生成动作 / 地点」时写草稿（只在手动点生成时调用） |
| **AstrBot 会话配置的 Provider** | 主人格自己的回复：回复方式 =「仅注入状态」时，以及接管失败自动降级时 |

**留空规则**：打杂模型留空 → 跟随看图模型；看图模型留空 → 跟随插件用模型。
老版本里分开配的「上下文压缩模型」「图片关系分析模型」现在都并进打杂模型，
读取老配置时会自动搬过去（关系分析本来就是纯文本，交给打杂模型更省）。

`llm_provider_id` 覆盖的四处调用：

| 调用点 | 什么时候跑 | 频率 | 干什么 |
| --- | --- | --- | --- |
| 接管回复 | 消息走到大模型那一刻（被 @、或意图路由放行） | 每条这种消息一次 | 生成 `reasoning` + `actions` |
| 自主行为决策 | 决策器评估时，规则给不出计划或 10% 抽样命中 | `llm_plan_min_interval_seconds`(900s) + `max_llm_plan_per_hour`(4) | 安排「接下来 15~30 分钟做什么」 |
| 自主发言文案 | 主动搭话 / 分享见闻 / 插话，且没有现成文案 | `max_llm_text_per_hour`(6)，超出后用内置短句池（零成本） | 写一句要发到群里的话 |
| 工具参数补全 | 工具型动作缺参数时 | 每个「工具 + 意图」一次（有缓存，每小时有上限） | 把意图翻译成工具参数（用 `helper_provider_id`） |
| 动作后续续说 | 做饭 / 看书 / 搜索 / 查天气完成后（`trigger=llm_followup`，以及工具动作拿到结果时） | 每个这类动作完成时一次 | 把结果讲成第一人称的见闻 |

续说这一类有个分寸约束：如果刚才没人在跟她说话，她会当成自言自语，不会写成在群里招呼全场，
也不会出现「想吃吗」「吱一声」这种吆喝句式（这些规则写死在续说提示词里，逐条改不了；
不想要续说就在动作的「完成后」选「什么都不做」）。

| 回复方式 | 被 @ 的回复 | 自主行为（计划 / 文案 / 续说 / 插话） |
| --- | --- | --- |
| 接管回复（默认） | **`llm_provider_id`** | `llm_provider_id` |
| 仅注入状态 | AstrBot 会话 Provider（主人格） | `llm_provider_id` |

**所以怎么选模型？**

- 这四处任务的共同点是：输入是结构化状态、输出是严格 JSON、文案都很短——**不需要文采，需要听话、稳定、快**，适合便宜档的模型。
- 但**接管回复决定了用户看到的回复质量**：人格设定会作为提示词第 1 层注入，可「人设演绎得好不好」取决于模型能力。很在意聊天质量的话，把回复方式切到「仅注入状态」，让主人格负责说话，这里只留给自主行为。
- **不要用推理型 / 思考型模型**：插件已经强制它输出 `reasoning` 字段，模型再内部思考一遍是双重开销，而且明显更慢。
- 插件**不强制 temperature**，用的是 Provider 自己的默认值；如果自主发言太飘或 JSON 老是解析失败，把那个 Provider 的温度调低再试。
- 模型弱到不能用也不会坏：动作解析失败会自动降级成「交回主人格回复」，用户那边看起来只是「她今天没动作」，不会没回应也不会报错。

另外提醒：`astrbot_plugin_intent_router` 的判断调用与上面两个来源都无关，它有自己的 `judge_provider` 配置（留空同样回落到会话默认）。

## 默认世界

六个地点：卧室、书房、窗边、吧台、厨房、大厅，连成一张小地图（每条连线都标了走过去的 tick 数）。
默认日程：

- `08:30` 走到大厅伸个懒腰
- `18:00` 去厨房做饭，做完会把这道菜讲给大家听
- `23:30` 回卧室睡觉（8 小时）

睡觉和小睡是两件事，说明里写清了使用场合：**睡觉**是睡一整晚（约 8 小时，夜里或精力见底时用，只能在卧室），
**小睡**是白天犯困时打的盹（10~60 分钟，卧室或大厅都行）。模型能不能挑对，取决于提示词里有没有
「现在是几点、什么时候段」——所以运行时状态的第一行就是当前日期时间。

默认动作按用途分四类：

| 类别 | 动作 | 特点 |
| --- | --- | --- |
| **互动类** | 抱抱、亲亲、摸摸头、笑、挥手、倒杯茶、伸懒腰、**戳一戳** | 模板文案 + 数值联动，零 token。文案里用 `{bot}`/`{user}`，例如「（{bot}抱了你一下）」，会替换成你在全局设置里填的 Bot 名称；「戳一戳」会真的发 QQ 的戳一戳（协议端不支持时退回文案） |
| **表达类** | 说话、分享、哼歌、听你说、打气 | 让大模型按人设说一句 |
| **生活类** | 睡觉、小睡、发呆、看书、做饭 | 时长由大模型在区间内决定，效果按"每持续 1 分钟"结算；看书和做饭做完还会接一段分享 |
| **工具类** | 上网搜索、查天气 | 内置动作，默认绑 `web_search` / `get_weather`，本机没装就自动换成本机装好的那个（搜索类、天气类各带一串备选）；一个都没装就跳过这一步并在日志里写明原因，编辑器也会在状态页和动作页提示 |

## 数值与状态

内部状态：`energy` `loneliness` `curiosity` `affect`(心潮) `valence`(效价) `boredom` + `mood`，
六个数值都真实驱动行为：

| 数值 | 谁在用 |
| --- | --- |
| 精力 energy | 决策器（<0.25 回卧室睡觉）、日程条件 `min_energy`、动作前置条件、睡觉恢复、极端保护（连续 3 天 <0.1 强制补觉） |
| 孤独感 loneliness | 决策器（>0.7 去大厅找人）、日程条件、极端保护（24h >0.9 强制找人） |
| 好奇心 curiosity | 决策器（>0.7 且在书房且有搜索工具 → 去上网）、搜索时消耗 |
| 心潮 affect | 情绪被激起的强度（不是开心程度）：和效价一起决定**心情词**和**这一轮的表达方式**、给记忆权重加成；被夸/被抱/吵架/被冷落都会推高它，之后自然回落到「静止位置」。**有边际递减**，见下 |
| 效价 valence | 心情的好坏（0.5 是中性）：由 `基线 + 短期偏移` 组成。基线跟精力/孤独/无聊/好奇与时段走（本身不存历史），偏移由事件产生、随时间归零。它决定"情绪朝哪个方向"，也决定插话的难度 |
| 无聊 boredom | 决策器（>0.8 换地方、>0.45 去看书）、看书/做饭降低 |
| mood | 由**情绪两轴**派生（心情词），精力低时加「困倦」修饰；动作也能临时覆盖（`mood:满足`） |

### 情绪两轴：心潮 × 效价

心潮（唤醒度）和效价（方向）是两个独立的轴：**心潮控制她有多激动，效价控制她激动成什么样**。
两者交叉出九种表达形态，同一个格子同时给出心情词和这一轮的说话约束：

| 心潮 | 效价 | 心情词 | 这一轮的表达方式 |
| --- | --- | --- | --- |
| 低 | 正 | 舒坦 | 1~2 句、60 字内，语气平和 |
| 低 | 中 | 平静 | 1~2 句，简短自然 |
| 低 | 负 | 低落 | 最多 1 句、20 字内；可以只做个动作代替说话 |
| 中 | 正 | 轻快 | 1~2 句，可以用语气词和表情 |
| 中 | 中 | 平静 | 1~2 句，不要长篇解释 |
| 中 | 负 | 不痛快 | 最多 1 句、30 字内，不解释也不勉强热情 |
| 高 | 正 | 兴奋 | 可拆 2~3 条短句，可用感叹号和语气词 |
| 高 | 中 | 心潮起伏 | 最多 2 条短句，别硬找话题 |
| 高 | 负 | 恼火 | 最多 1 句、15 字内；优先用动作回应，不想说就不说 |

这几条约束是**硬上限**：群聊里最多 2 条、私聊最多 3 条，并且和「说话密度提醒」冲突时取更严格的一条。
关掉「全局设置 → 说话节奏 → 让心情影响这一轮的说话形态」就回到纯人设风格。

两条时间规律：**事件只负责拉高，不负责维持**（脉冲当场生效，之后按真实时间回落到基线，
和 tick 长度无关）；**基线只跟五维与时时段有关**（本身不存历史，所以"最近心情一直不好"需要慢慢积累）。

### 安全阀

效价长期偏低（<0.25 持续 30 分钟）会做两件事：

1. 把效价偏移**减半**（拉回基线，而不是硬设一个好心情）；
2. 让自我调节类的动作更容易被选中（发呆 / 去看书的门槛下调），并给她一句
   「你现在更想自己待会儿」——这是行为倾向，不是被安排一个动作。

另外效价 <0.2 持续 30 分钟会关掉「想被注意到」那条插话动机，且至少关 15 分钟
（避免阈值边上反复抖）。「想发作」那条不受影响：被惹毛的人反而是想开口的。

另外这些数值都会：每 tick 自然演化、被地点氛围调制、被事件（被 @、被抱、群冷清…）和动作效果改变、

### 心潮的边际递减

心潮是「情绪被激起的强度」，所以**不是线性叠加**的：越高的时候，同样的刺激能加进去的越少
（最低保留 25% 效力）。这样普通闲聊只会让她有一点起伏，要真正「难以平静」得靠亲密或强烈的互动。

配合两条调整：普通消息的加成从 `+0.08` 降到 `+0.02`（被 @ 时 `+0.06`），回落速度从
`0.012/分钟` 提到 `0.02/分钟`。模拟一个很活跃的群（每分钟约 1 条消息、20 分钟夸她一次）两小时：

| 时间 | 旧规则 | 现在 |
| --- | --- | --- |
| 10 分钟 | 0.88（直接顶到「难以平静」） | 0.37 |
| 60 分钟 | 0.88 | 0.53 |
| 120 分钟 | 0.88 | 0.56（心潮起伏） |

想让情绪更敏感或更迟钝，调「状态变化速度 → 心潮回落/分钟」，以及动作里的心潮效果。
并写进提示词——所以数值不是装饰，而是真的在决定下一步做什么。

## 无人回应保护

主动发言后会等待 `silence_window_minutes`；没人回应就累加 `unanswered_count`，
达到阈值进入冷却（`cooldown_after_unanswered` 分钟），冷却期间不主动发言，
冷却结束后计数减半。计数 > 0 时会写进提示词，让她说话更犹豫。

## 孤独感与插话

**孤独感（`loneliness`）负责"她想不想找人说话"，心潮 + 效价负责"她说话成什么样"**——
这两件事以前都由社交欲兼着，阈值各自调很容易互相打架，后来拆开了。

系统会保存最近一段时间的群聊内容
（默认时间窗 20 分钟、最多 12 条，按时间自动过期），群里最近确实有人在聊
（窗口内消息数 ≥ `min_messages_to_interject`，默认 2 条）时，**下面两条动机满足一条**就会想开口：

| 动机 | 条件 | 说出来是什么样 |
| --- | --- | --- |
| A 想被注意到 | 孤独感 ≥ **浮动阈值**，且效价 > 0.35 | 由风格格决定；心情差时会更短 |
| B 想发作 | 心潮 ≥ 0.6，且效价 < 0.35 | 通常一条短句，或者干脆只戳一下 |

**阈值是浮动的**（不是浮动意愿值）：心情越差越难开口，最多 +0.10；效价 <0.2 持续 30 分钟会再抬到
+0.15 并关掉动机 A（至少关 15 分钟）。开口之后的形态仍归风格格管，两件事不混在一起。

另外还要同时满足：

- 距离上次插话超过 `interject_cooldown_minutes`（默认 20 分钟）；
- 没在无人回应冷却里，也没超每小时自主上限；
- 没处在"刚回过话"的主动发言冷却里。

插话文案由大模型根据「最近群里在聊」的上下文现场生成；如果她说不出什么就保持安静，不会硬凑。
总开关和这组参数都在「全局设置 → 孤独感与插话」里。

**想知道是谁在限流**：状态页的「互动与运行」里会显示本小时的插话统计
（想插话几次、被插话冷却 / 无人回应 / 回复后冷却 / 每小时上限分别拦下几次）——
光看频率数字看不出瓶颈在哪，这几个计数才能说明问题。

隐私：只保存最近 N 条、按时间自动过期；命中内容安全屏蔽词的消息不会记录。

## 睡觉与打断

她睡着（或小睡）时不会跟人聊天。这道门禁挡在**两条回复路径之前**，比「接管 / 注入」的岔路口还早：

| 情况 | 结果 |
| --- | --- |
| 睡着了，有人 @ 她但没有唤醒词 | 只回一句固定文案（默认 `zzz…（{bot}睡觉中，要叫她起来吗？）`），不调大模型、不执行动作、不写互动记忆 |
| 睡着了，消息里带唤醒词**且** @ 了她 | 打断睡眠：停下当前动作、清掉排队的计划、给一段保护期，然后正常回复；同一条消息里交代的事照做 |
| 睡着了，群里别人说话（没 @ 她） | 整条消息被挡下：不回复、也不交给主人格，**其它插件也不会执行**（省掉一次判断） |
| 没在睡 | 一切照旧 |

「在跟她说话」只认**消息里真的 @ 了她**（或私聊）。这点很重要：意图路由那类插件放行消息时会把
`is_wake` 置 True，那是"这条消息要交给大模型"，不等于"有人在跟她说话"——只看那个标志的话，
睡着时它会以为有人在叫她，反而回一句 zzz。

配置在「全局设置 → 睡眠与打断」：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| 睡觉时被叫怎么办 | 回固定文案 | 也可以选「完全不回」或「照常回复」 |
| 固定文案 | `zzz…（{bot}睡觉中，要叫她起来吗？）` | 支持 `{bot}`（她的名字）和 `{user}`（叫她的人）；留空等于不回 |
| 唤醒词 | 醒醒 / 起床 / 别睡 / 醒来 / 起来啦 / 别睡了 | 回车或点「添加」加一个，点词上的 × 删掉 |
| 必须 @ 她才算叫醒 | 开 | 群里有人随口说「起床了」不会把她弄起来 |
| 同一条回复的最短间隔 | 5 分钟 | 连着被 @ 也不会刷一屏 zzz，冷却期内保持安静；填 0 表示每次都回 |
| 叫醒后多久内不再自己睡 | 12 分钟 | 刚叫醒时精力往往还很低，没有这段保护期，规则几分钟内又会把她送回床上 |
| 小睡也按睡觉处理 | 开 | 关掉后只有「睡觉」会被拦，打盹时照旧聊天 |
| 叫醒时清空排队的计划 | 开 | 否则她被打断时排在后面的动作（例如几小时前想说的那句话）会在睡醒后突然补发 |
| 睡着时连其他插件一起挡下（方案 A） | 开 | 关掉就退化成「方案 B」：只保证本插件不出声，别的插件照常处理 |
| 挡住哪些消息 | 只挡没 @ 她的 | 也可以选「除指令和唤醒词外全挡」（连固定文案也不回） |

叫醒之后群名片也会立刻从「睡觉中」改回来，不用等名片同步那 60 秒冷却。

### 阻断是怎么做到的

挡下这条消息的钩子注册在**比意图路由更高的优先级**（意图路由是 100，这里取 200）。
AstrBot 的处理器按优先级从高到低执行，而 `event.stop_event()` 会让后面的处理器不再执行
（`StarRequestSubStage` 每轮都检查 `event.is_stopped()`）。所以睡着时：

- 没 @ 她的消息：在这里就被截住，意图路由根本不会跑，既省一次判断，也不会把睡着的她拖进对话；
- `@她`：放行 → 回固定文案；带唤醒词的 → 叫醒；
- `/指令`：永远放行（否则 `/vw status`、`/vw 叫醒` 这些就用不了了）。

被挡下的消息仍然会记进她的聊天留档，醒来能看到群里发生过什么。

**和意图路由的配合（方案 C）**：插件在状态快照里多给了一个 `sleeping` 字段。装了
`astrbot_plugin_intent_router` 时，它会读到这个字段并把放行阈值推到 1 以上（任何置信度都不放行）——
两端的判断口径一致：**她睡着 = 不判断**。即使把「方案 A」关掉，也不会再出现"睡着还被拉去回话"。

### 被叫醒时提示词会说什么

两种回复模式都会带上同一句：

> 你刚被叫醒，可以迷糊一点；但对方如果在同一条消息里交代了要做的事，先把那件事写成动作，再回一句话。

消息里除了唤醒词还说了别的（例如「醒醒，去书房帮我查新闻」）时，再加一句
「对方不只是叫你起来，还交代了事情」。这样既保留"刚醒"的演出，又不会出现
「只应了一声、把她交代的事忘了」。

日志页能看到这道门禁做了什么：`她在睡觉，只回了一句固定文案：…`、`她在睡觉，没有回复（…）`、`被 xxx 叫醒`。

## 她多久会自己动一次

### 一轮里的多个动作会排队

她手头有正在做的事时也可以照常安排接下来的动作：**新的安排会排队，等手上这件事做完接着做**，
不会被打断，也不会把她原本没做完的安排顶掉——原来剩下的步骤会接在新安排后面（先做主人刚说的，再回去做她自己的）。

**明确的打断**：如果对方说的是「别做了 / 不用了 / 停」，她可以真的停下来。这时模型会在回复里
带一个 `cancel` 字段，两档：

| 取值 | 行为 | 典型说法 |
| --- | --- | --- |
| `now` | 立刻停手，并放弃还没做的安排 | 「别查了」「停下来」 |
| `queue` | 手上这件做完，但不要再按原计划走 | 「后面的不用了」 |

**模型写了就照做**：不再拿"消息里有没有『别』字"当门槛——否则会出现她嘴上说不干了、
身体还在接着干的情况。提示词里已经限定"只有对方明确要求时才写"，写错由模型负责。
唯一的例外是动作自己标了「不可打断」（例如睡觉）：那件事不做一半就扔，但剩下的安排照样放弃。
每次取消都会在日志里留一条「按对方说的停了」。不想依赖模型的话，用 `/vw debug stop` 直接停手 + 清空安排。

如果她一次决定"先去书房，再上网查"，插件会先开始走路，把后面的动作排进计划，
等上一个动作做完再接着做——不会边走边说，更不会后一个动作把前一个顶掉。

### 走到一个新地方会就地做一次决策

她特地走到某个地点后，插件会**立刻**看看"这儿能做什么"，而不是等下个评估周期：
这一步直接问大模型，不看概率抽样、也不占「每小时最多自主行动次数」的额度
（它有自己的上限「每小时最多抵达决策次数」，默认 12 次，在「说话频率与预算」里调）。
所以像"让她去书房查新闻"这种事，走到之后就会接上搜索，不会愣在那儿。

### 「想做的事在别的地方」怎么处理

动作可以限定「只在某个地点可用」（例如上网搜索只属于书房）。遇到这种情况有两道保险：

1. **提示词要求她一次写全两步**：可达表里写明了每个地方能做什么、走过去要几 tick，
   协议里也有硬规则——「想做只有别处能做的事，必须写两步：先 walk_to，紧接着把要做的那件事
   也写进同一串 actions（只写移动不算安排）」，以及「在 say 里承诺了要做什么，就必须把动作也写进 actions」。
   写成一步是她最容易犯的错：那样插件只好带她走过去，到了之后再问一次模型要做什么，白白多花一次调用。
2. **万一她只写了动作、忘了写移动**：插件会替她补上那一步（日志里标注
   `↪ 她想去别处做这件事，已自动前往「书房」`），到了之后再执行那件事。
   这一层可以在「全局设置 → 动作与地点」里关掉：关掉后就变成"只有眼前能做的事才会被执行"，
   场景感更强但也更容易出现"她答应了却没做"。

真到了"落地后现决定"这一步（例如她只是想过去看看），那次调用也不是空的泛泛规划：
提示词会直接告诉她「你刚刚特地走到了「书房」，因为你打算：…，这里能做：…」，
让她一次就把该做的事排出来，而不是重新规划一整段时间。

注意：如果模型**连动作都没写**（只回了一句话），插件没有任何东西可以补救——
这种情况只能靠提示词降低概率。日志里现在会显示 `〔动作：say〕`，
一眼就能看出"她只说了话、没安排动作"。

### 日志里能看到什么

每条回复事件现在带三样以前看不到的东西：

- `〔动作：…〕`：这一轮解析出来的动作清单；
- `⚠ …`：被丢弃的动作及原因（例如"动作 fly 在当前场景不可用，已丢弃"）；
- 事件详情里的 `raw`：**模型的原话**（截断保存），用来判断是"模型没写"还是"被丢了"。

工具调用则统一记一条 `tool` 事件：调用哪个工具、**实际传出去的参数**、
返回了什么；失败时记 `✗ 失败：原因`，并且不会触发"就着空气说一段"。

自主行为这条链上有四个闸门，从外到内依次是：

| 闸门 | 在哪配 | 默认 | 作用 |
| --- | --- | --- | --- |
| 评估间隔 | 插件配置 → `decider_interval` | 300 秒 | 每隔多久评估一次「她现在想不想做点什么」 |
| 每小时上限 | 全局设置 → 每小时最多自主行动次数 | 2 次 | 一天里最硬的闸门：平均最快每 30 分钟做成一件 |
| 规则决策 | 动作/地图配置 | — | 困了回卧室、孤独了去大厅、无聊了换地方、好奇了去查东西、群里热闹又孤独就插一句 |
| 问大模型的概率 | 全局设置 → 自主决策 | 5%~40% | 这一次要不要**额外**交给大模型安排更丰富的计划 |

关键点：**规则决策不看那个概率**。规则命中就直接执行——比如她无聊值超过 0.8 想换地方，
这一轮就会安排移动，跟抽没抽中没关系。概率只管「要不要再问一次大模型」，
问到了就用大模型的计划（更细致、更贴合上下文），没问到就用规则的计划。

概率不是写死的，而是按**决策意愿**在两个上下限之间线性插值：

```
概率 = 下限 + (上限 − 下限) × 决策意愿
决策意愿 = 0.45×孤独 + 0.20×无聊 + 0.10×好奇 + 0.15×心潮 − 0.35×疲惫 − 被冷落惩罚
```

所以她是"闲得慌"还是"刚忙完很平静"，被问到的频率明显不同（实测，默认 5%~40%）：

| 状态 | 决策意愿 | 问大模型的概率 |
| --- | --- | --- |
| 平静待着 | 0.08 | 7.6% |
| 有点无聊 | 0.21 | 12.4% |
| 很孤独 | 0.42 | 19.7% |
| 心潮很高 | 0.41 | 19.2% |

想让她更常被大模型安排事情，把「概率上限」调到 0.6~0.8；想省 token、让她按规则过日子，
把上下限都压到 0.05 以下。当前意愿和实际概率会显示在「实时状态」页的顶部状态卡上。

### 把过程发到群里看（调试回显）

排查"她为什么这么做"时，翻日志页不方便，可以直接让过程出现在群里：
「全局设置 → 调试输出」里**勾选想要的类型**（配置项 `world.echo_types`，默认一个都不勾 = 关闭）。
类型按用途分成六组（决定与动作 / 工具与指令 / 记忆与回想 / 日程 / 睡眠与保护 / 图片·上下文·名片），
每组可以单独全选或取消，旁边还有「全选 / 常用 / 清空」三个总控按钮。

同一块里的**「精简模式」**（`world.echo_compact`）勾上后只发要点、不发参数和结果：
排查"她做了什么"够用，也不会把群刷满。

开启后，回显的是**群里本来看不见的那些环节**——她自己说出口的话本来就会正常发出去，
不会再重复一遍。以"日程到点去书房查新闻"为例：

```
▶️ 开始「移动」，预计 1 个 tick，目标「书房」
✅ 做完「移动」
🔧 调用「web_search」参数 {'query': '今天的新闻'}
📥 「web_search」返回：今天有三条科技新闻…
查到啦，今天有条开源模型的消息。      ← 这句是普通的 say，只发一次
```

回显按**实际发生的先后**发出去：先调工具、拿到结果，然后才是她开口说话——
上面这个顺序就是群里刷出来的顺序。

可以勾选的类型和它们的前缀：

| 勾选项 | 前缀 | 事件 |
| --- | --- | --- |
| 她的决定 | 🧠 | 这一轮定了什么计划、为什么定、是谁定的（规则 / 大模型 / 日程 / 极端保护） |
| 开始动作 | ▶️ | 开始一个动作，带预计耗时；移动还带目标地点 |
| 动作完成 | ✅ | 持续动作做完，带工具返回结果 |
| 静默动作的内容 | 🎬 | 想事情这类本来不发到群里的动作写了什么（她自己说过的话不会重复发） |
| 调用工具 | 🔧 | 调了哪个工具、**实际传出去的参数** |
| 工具返回 | 📥 | 工具返回了什么；失败会写明原因 |
| 触发指令 | 🧩 | 指令型动作实际发出去的指令 |
| 指令返回 | 📤 | 那条指令返回了什么、有没有跑失败 |
| 被跳过的动作 | ⏭️ | 某个动作没做成的具体原因（缺必填参数、地点不对、工具不存在…） |
| 写了一条记忆 | 📝 | 一段对话被总结成记忆时发出来，方便对着看记得准不准 |
| 群名片变化 | 🏷️ | 她的群名片改成什么、有没有改失败 |
| 进入安静期 | 💤 | 连续主动说话没人回应，触发无人回应保护 |
| 极端保护 | 🚨 | 精力透支、太久没人说话这类兜底规则被触发 |
| 上下文压缩 | 🗜️ | 群聊留档攒太多、被压成摘要的时候 |
| 日程开始执行 | 📅 | 哪条日程开始跑了、是到点还是你点了「立即执行」、这一串要跑哪些动作 |
| 触发指令 | 🧩 | 指令型动作实际发出去的指令与对方的返回 |
| 被叫醒 | 🌅 | 她睡觉时被唤醒词叫起来 |
| 睡着时的回话 | 😴 | 睡着时被 @，只回了一句固定文案 |
| 睡着时没回复 | 🤐 | 睡着时被消息叫到，但按配置保持安静 |

只想要"她到底做了什么"，勾「常用」那六项（决定 / 开始动作 / 动作完成 / 静默动作 / 工具调用 / 被跳过）就够；
排查记忆准不准、睡觉门禁有没有生效时，再把 📝 / 🌅 / 😴 / 🤐 打开。

一段完整的日志长这样（含被跳过的情况）：

```
🧠 决定：上网搜索　〔原因：为了做「上网搜索」先移动过去；来源：auto_travel〕
▶️ 开始「移动」，预计 1 个 tick，目标「书房」
✅ 做完「移动」
⏭️ 跳过：工具动作「上网搜索」缺少必填参数 ['query']
```

这些消息只是播报，**不算她说过的话**：不会进聊天上下文、不会累加"主动发言没人理"的计数，
也不影响她的状态数值。所以可以放心在调试期间开着，排查完在同一个卡片里关掉即可。

想看到更细的（提示词原文、指令与参数、工具返回全文）还是看后台日志：那属于「插件配置 → 调试日志」。

## 天气

天气是**全局的一份**（所有会话共用，也不分地图区域），存在状态库里，重启后还在。

- **她主动查**：动作「查天气」拿到结果后，除了照常说一句，结果也会存下来当背景。
- **后台静默查**：每 `refresh_hours`（默认 2 小时）查一次，**不发消息**、不触发续说。
  她主动查过之后，这个倒计时从头算。「所属城市」填了就直接按它查，不用模型猜。
- **写进提示词**：运行时状态里多一段——

  ```
  # 外面的天气
  外面的天气（2 小时前查的）：武汉｜26℃｜多云｜湿度68%｜东南风3级｜夜里转小雨
  ```

  「多久之前」按自然日算：今天说「X 小时前」（不到 1 小时写「刚刚」），
  昨天、前天直说，更久写「X 天前」。超过 `stale_hours`（默认 24 小时）之后，
  这一段整个不再出现——**她觉得过时了就别拿来当现在说**。
- **结果先归一化**：工具返回的可能是文字，也可能是天气截图。截图先交给看图模型读成文字，
  再交给打杂模型压成上面的「城市｜温度｜天气｜湿度｜风力｜预报」一行；哪一步没配、或者读不出来，
  就退回原文，绝不编。关掉「把结果整理成一行」就直接存原文。
- **地图页横幅**：编辑器「地图」页画布内部上方显示当前天气（图标 + 城市 + 描述 + 温度 + 多久之前），
  右边有「刷新」按钮可以立刻查一次。太旧的天气横幅照常显示，只是标着「X 天前查的」。
- 后台查天气需要一条真实消息当上下文（AstrBot 的工具要求如此）：群里还没人说过话时会自动跳过，
  等下一轮再说；工具没选好、没装好时也一样跳过并写进日志（调试输出里可选「天气」这一类）。

## 性别与称呼

全局设置里的「性别」（女 / 男 / 塑料袋）决定文案里的称呼：`她` / `他` / `ta`。
影响范围包括编辑器界面文字、`/vw status` 等指令输出，以及模板文案里 `{bot}` 的兜底称呼。
改完记得点右上角「保存」。

## 群名片显示什么

文案写在**它自己身上**，从上往下依次生效：

1. **动作的「执行中名片文案」**（动作编辑页里写，例如做饭动作写「做饭中」）——
   她在做这件事时显示它，「在做什么」优先于「在哪儿」；
2. **地点的「在这里时名片文案」**（地点属性里写，例如书房写「在书房」）——
   她只是待在那儿、又没在做带文案的动作时显示它；
3. 都没有就显示她原来的名片。

文案跟着动作 / 地点走，换预设时它们一起换，所以不会出现"预设里没这件动作、名片却还写着它的名字"。
老配置里那张 `状态 → 文案` / `地点 → 文案` 的全局表在升级时会被搬进对应的动作和地点，
表本身只留作兜底、不再出现在编辑器里（冷启动的「刚醒」这种没有动作对应的状态由内置默认值负责）。

改名本身还有开关、模板（`{base} | {status}`）、最大长度、改名冷却这些通用规则，在「全局设置 → 群名片同步」。

## 谁能用管理指令

`/vw` 里会改东西的那几条（重载配置、重置状态、恢复默认、改群名片、跑日程、调试命令、管理会话白名单）
需要管理员权限：

- AstrBot 自己的管理员**始终**可以（所以不会把自己锁在外面）；
- 另外可以在「全局设置 → 管理员 QQ」里再列几个人，让群里的管理员也能用这几条指令。

只读的指令（`/vw status`、`/vw memory`、`/vw recall`、`/vw help`）任何人都能用。

## 推理草稿 reasoning

开启后（默认开），大模型在给出动作之前必须先写一段草稿：

```json
{
  "reasoning": {
    "env": "书房，桌上摊着书",
    "state": "刚醒不久，精力一般",
    "mood": "平静",
    "who": "小明在问我周末怎么安排",
    "intent": "随口应一句，然后去泡杯茶"
  },
  "actions": [ { "type": "say", "messages": ["周末啊……还没想好"] } ]
}
```

- **顺序即推理**：模型是一个 token 一个 token 生成的，`reasoning` 写在前面，它的 token 就成了后面
  `actions` 的上下文——这才是真正的"先想后说"。
- **草稿永远不外发**：不进群聊、不计入动作数量、不写进记忆，只记在事件日志里，方便排查"她为什么这么回"。
- **强制读上下文**：让她复述"我在哪、什么状态、什么心情、在和谁说话"，能明显减少
  "提示词说在书房、回复却在厨房"这类低级错误。
- 服务端会**强制把 `think` 动作排到最前面**，不依赖模型给出的顺序；模型没写 `reasoning` 时只告警，不会失败。

推理草稿会让每轮多输出几十个 token，觉得费可以在「全局设置 → 基础」里关掉。
`actions` 里的 `think` 是另一回事——那是真正想留下的内心话，会写进内心记忆。

## 被 @ 时由谁回复

「全局设置 → 基础 → 被 @ 时的回复方式」：

- **接管回复（默认）**：她按自己的动作系统回应，能触发 hug / kiss / 去做饭 / 去搜索这类真实动作，
  数值也会真的变化（这些在纯注入模式下只能算文字描述）。
- **仅注入状态**：交回主人格用自然语言回复。

接管失败（没配模型、模型报错、模型没给出任何动作）时自动降级为注入，保证用户不会收不到回应。
历史对话会通过 AstrBot 的 `contexts` 原样带给模型，所以接管不等于失忆。

**她自己在忙的时候也会回你。** 插件自己在调模型（自主决策、动作续说、记忆总结、图片转述、
工具补参）时，打的是「这一条协程」的标记，所以这段时间里进来的消息照常走接管和睡觉门禁——
不会出现"这几秒里 @ 她没反应、只有主人格随口回一句"。

**同一条会话里连发的消息会排队。** 前一条还在等她开口，后一条就先等着（最多等 25 秒，
超时就不再等、宁可她多说一句），这样第二条看得到第一条刚说了什么，不会自顾自地重复回应同一件事。

## 与其他插件联动

### 智能意图路由（astrbot_plugin_intent_router）

那个插件负责判断「群里的哪条消息值得主人格回复」。本插件提供只读接口
`social_snapshot(session_id)`，任何同进程的插件都能拿到她此刻的孤独感 / 心潮等状态。

intent_router 侧新增了配置项：

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `link_virtual_world` | 开 | 是否启用联动 |
| `vw_threshold_max` | 0.75 | 孤独感 = 0 时的放行阈值（更安静） |
| `vw_threshold_min` | 0.3 | 孤独感 = 1 时的放行阈值（更愿意接话） |
| `vw_cache_seconds` | 10 | 读取状态的缓存秒数 |

效果：她在虚拟世界里越孤独，意图路由的放行阈值越低，越容易被叫去回消息；
她累了、无聊、不太想说话时会明显更安静。会话没加进虚拟世界白名单时自动沿用固定阈值。

注意插件加载顺序：intent_router 可能比本插件先加载，所以它启动时探测不到是正常的，
运行期第一次判断消息时会自动生效并打日志。

### 其他插件

注入提示词时是**追加**而不是覆盖，所以上下文理解、图片转文字等插件写进去的内容都会保留，
并且会被带进接管模式的提示词里；工具裁剪只针对白名单会话，且可以整体关闭。

**靠回复标记工作的插件**：有一类插件要求大模型在回复末尾写一个标记（例如 `[好感度增加1]`），
它们自己在回复钩子里解析并抹掉这个标记。接管模式下是插件自己调模型、自己发送的，
这条钩子默认轮不到跑，标记就会白写。打开插件配置里的 `reply_hook_bridge`（默认开）之后，
接管的回复会先经过 AstrBot 的「LLM 响应后」和「发送前」两道钩子再发出去，
所以这类插件照常工作，注入模式则本来就天然兼容。

同一个开关还会把接管流程的其它几个生命周期钩子**按同样的时机补发一遍**，因为接管时
AstrBot 的管线轮不到跑：准备调模型前 → `on_waiting_llm_request`；调用 AstrBot 工具前后 →
`on_using_llm_tool` / `on_llm_tool_respond`；消息发完 → `after_message_sent`。
靠这些钩子工作的插件（典型的是「开始处理时贴个表情、处理完摘掉」）在接管模式下才不会漏掉一半。

## Token 预算

自主行为默认很省：模板动作不调 LLM，一次 LLM 计划覆盖 30 分钟（`plan_valid_duration`），
并且有四道闸门防止空群里"自言自语烧 token"：

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `limits.llm_plan_min_interval_seconds` | 900 | 两次「问 LLM 要计划」之间至少隔 15 分钟 |
| `limits.max_llm_plan_per_hour` | 4 | 每小时最多 4 次 LLM 计划决策 |
| `limits.max_llm_text_per_hour` | 6 | 每小时最多 6 次 LLM 生成发言，超出后用内置短句池（零成本） |
| `limits.max_arrival_decisions_per_hour` | 12 | 每小时最多 12 次「走到新地方就地决策」；这类决策不占自主行动额度，单独限流 |
| `limits.forced_plan_min_interval_seconds` | 3600 | 极端保护（强制睡觉/找人）最短触发间隔 |

注意：**接管回复**每条消息都要跑一次完整的五层提示词，这是这个插件最大的 token 开销来源；
如果只想要"她知道自己在哪"这层认知，把回复方式切回「仅注入状态」会便宜很多。

### 提示词分层与前缀缓存

五层的顺序是**按"越稳定越靠前"**排的，这样前面那截可以整个会话复用，吃到 provider 的前缀缓存：

| 层 | 内容 | 变化频率 |
| --- | --- | --- |
| 第 1 层 | 人设 | 不变 |
| 第 2 层 | 世界规则 | 不变 |
| 第 3 层 | 输出格式（JSON 契约、字段说明、通用规则） | 不变 |
| 第 4 层 | 当前场景（氛围、这里能做什么、可达表） | 换地点时变 |
| 第 5 层 | 运行时状态（数值、记忆、群聊上下文…） | 每次调用都变 |

所以能命中的前缀是**前 3 层**（默认配置下约 1.7k 字符），而不是只有前 2 层。
为此做了两件事：

- 能把哪些 `type` 是随地点变的，所以**不放在固定的第 3 层**，而是放在第 4 层；
  第 3 层里不出现任何地点名、动作 id，改地图也不会把缓存打散。
- 「问计划」和「生成回复」共用第 1、2 层——两种调用能吃到同一段前缀。

代价是"格式要求在提示词中间"会稍微削弱它的存在感，所以最末尾补了一段三行的
「最后确认」当近因锚点：只输出 JSON、reasoning 写在前面、别重复最近说过的话。

> 缓存是否生效取决于 provider：DeepSeek / OpenAI 这类服务对相同前缀自动降价（通常要求前缀
> 达到一定长度），本地部署或不做缓存的 provider 则没有区别。想让缓存更值，别把易变内容
> 写进人设或世界规则里。

## 状态、记忆与存储

- `state.db`（SQLite，WAL）：每会话 `WorldState`、场景记忆、关系、事件日志、键值、日程触发记录
- `world.json` / `schedules.json` / `sessions.json`：可读可改，编辑器直接写这些文件
- 记忆按作用域存储（group / persona / group_persona / global / node），召回时按配置过滤并打分
  （权重 × 用户匹配 × 节点匹配 × 时间衰减 × 召回惩罚）
- 记忆冲突策略：`newest`（默认）/ `highest_weight` / `skip_conflict`
- 记忆衰减：30 天半衰期（只在**召回打分**时打折，不会因为年纪大而被删掉）；
  条数上限是每个「会话 + 人格」500 条，超了才按权重从低到高淘汰
- **权重不是写死的**：写入时会按「这段经历的情绪有多强」加成——
  显式情绪标签、mood、正文里的强情绪词（生气 / 吵架 / 心疼 / 别走…）取最大值，
  再加心潮 × 0.15。所以吵架、表白这类记忆比"今天天气不错"更容易被想起来。

### 对话是怎么变成记忆的

**主动回想（内置动作「回想」）**：她可以自己想回忆点什么——按主题（「想想在厨房做饭的事」）、
按地点（「回忆一下书房里的事」，只看那个地点）、或者按区域（「回忆公园里的事」，翻该区域下所有地点）。
不写地点就是跨地点找，当前所在地点只是更容易被想起来。回想是瞬时动作，也不需要她在同一次输出里再写别的动作：
插件翻完记忆会**带着回忆到的内容再问她一次**，那时她才开口；什么都想不起来时会照实说，不会编。
刚被想起过的记忆会有一段时间"轻一点"（默认 2 小时窗口、最多打对折，可调），出了窗口自动恢复。
「调试输出」里勾上「回想开始 / 回想完成」就能看到她想回忆什么、翻到了什么。

逐条存「某某说了什么」几乎没有信息量（同一个人连说五句就是五条），所以对话是**攒成片段再总结**的：
聊天内容先进一个待总结的缓冲，等到**触发点**才让大模型把它压成一句以她的视角写的记忆，
例如「小明今天加班到很晚，说自己快撑不住了，我有点心疼」。

| 触发点 | 说明 |
| --- | --- |
| 这段聊完了 | 距最后一条对话超过「聊完多久算一段」（默认 30 分钟） |
| 攒够条数 | 同一段对话达到「攒够多少条总结一次」（默认 10 条，含她自己说的话） |
| 她换了地点 | 走开时把刚才在那个地点聊的内容总结掉，记忆挂在**原来那个地点**上，下次回到那里能想起来 |

只有她自己说话（自言自语、一个人做事）时，总结会以「我做了什么、当时怎么想」来写，
不会去追问"对方是谁"；万一模型还是写出这种反问句，这句话会被丢掉、改用她自己的原话兜底。

具体调用时机是每个 tick 检查一次（不占会话锁，不会拖慢消息回复）。这三个开关和长度上限都在
「全局设置 → 记忆」里；把「把对话总结成记忆」关掉，聊天内容就完全不进记忆。

两个细节：

- 模型在回复 JSON 里顺手给的 `memory` 字段**只是写记忆时的提示**（会一起喂给总结的那次调用），
  不再单独存成一条；
- 模型不可用时退化成一行摘录（「小明说「我今天加班到现在才下班」」），而不是什么都不记。

## 常见问题

**她完全不动？** 检查会话是否在白名单里（`/vw session add`）、插件是否启用、
`tick_interval` 是否过大。用 `/vw debug state` 看 `world_time` 有没有涨。

**改完配置要手动热加载吗？** 不用。编辑器右上角只有「保存」，保存成功会**自动热加载**并提示
「已保存并生效」。唯一例外是 AstrBot 插件配置页那一份（Provider、tick 间隔、密码…），
那份改动要在 AstrBot 那边点热加载或重启才生效。

**她一直在说话 / 从不说主动话？** 调整 `limits.max_autonomous_per_hour` 与
`limits.max_share_per_hour`；`decider_interval` 决定她多久评估一次；
「孤独感与插话」里的阈值和冷却决定她多爱接话；无人回应保护会让她安静下来。

**她睡着的时候还在群里聊天？** 看「睡眠与打断 → 睡觉时被叫怎么办」是不是被改成了「照常回复」，
以及唤醒词是不是写得太宽（比如把「早」也加进去，那她每天都会被正常问候叫醒）。
她睡着时的判定只认「@ 她 + 唤醒词」，两条都不满足才走固定文案。

**后台一直报「发送消息失败 / Timeout: NTEvent …sendMsg」？** 这是 QQ 协议端（NapCat/Lagrange）
没等到 QQ 客户端内核确认，属于平台侧问题（协议端掉线、客户端卡死、被风控或禁言）。
插件这边**失败就失败，不会重发**：

- 同一个会话发送失败后进入 **180 秒冷却**，期间连平台都不碰（避免把更多消息塞进协议端队列，
  恢复后一次性喷出来）；冷却期内同一批剩下的消息也不再尝试；
- 接管回复同样只发一次——以前"失败就换一条通道再发一遍"的兜底已经去掉，
  因为超时经常是"其实已经发出去了"，补发就变成刷屏；
- 失败会记一条 `send_failed` 事件（日志页能看到"这条没能发出去（原因）：内容"），
  后台日志每个冷却窗口只打一条，不会刷屏。

**群名片一直报错？** 失败会按 5 分钟起、逐次翻倍退避（最多 1 小时一次），
成功或状态变化后重置，不会再每分钟重试一次。

**@ 她没反应？** 看后台日志有没有「接管未生效」；常见原因是没配 Provider、
模型返回的不是 JSON、或模型没给出任何动作（这三种都会自动交回主人格）。

**模型把思考（thinking）也吐出来了，甚至发到群里？** 有些模型 / Provider 不认
「关闭思考」这类参数，偶尔还会漏掉开标签、只留一个 `</thinking>`。插件在解析前会先剥掉
`<thinking>…</thinking>`、`</thinking>`、```` ```thinking ```` 这几种残留，再去找 JSON：

- 剥完之后是合法 JSON → 正常执行，思考一个字都不会进群；
- 剥完之后只剩长文 / 半个 JSON → **什么都不发**（只记一条警告），不会把思考当发言糊到群里；
- 剥完之后是一句短话 → 按"她直接说了句话"发出去（这是模型没走 JSON 协议时的老兜底）。

想在日志里核对，看那条 `reply` 事件的 `raw`（模型原话）和 `warnings` 就行。
要彻底不思考，得换一个听话的模型或 Provider——插件这边只能容错，不能替模型闭嘴。

**工具动作没反应？** 确认动作里选的工具在 AstrBot 里真的注册了（`/vw tools` 可以看当前能用的工具）；
工具调用需要该会话最近有过消息事件（插件会用最近一次事件作为调用上下文）。

**群名片不变？** 发送 `/vw nickname`（不带参数）会直接告诉你现在的情况：
原名是什么、当前名片是什么、按当前状态应该显示什么、有没有被锁定、冷却多久。
编辑器「实时状态」里的名片一栏只有一个「锁定 / 解锁」按钮，按钮文字就是当前状态的下一步操作
（锁定中会显示「解锁」，并且按钮变亮），旁边是「保存名片」和「恢复原名」。

名片按这个顺序算：`原名 | 状态文案`。
**原名**依次取「插件抓到的她当前群名片」→「全局设置里的 Bot 名称」——
全新安装时第一条要等群里有过消息才能抓到，所以建议先在「全局设置 → 基础 → Bot 名称」里填一个名字。
**状态文案**来自「全局设置 → 群名片同步」里的「状态 → 名片文案」和「地点 → 名片文案」，
两边都没配就会保持原名不动。

改名片失败时不再静默：日志页会出现一条「群名片」事件，写明原因，常见的是——
当前平台不支持（只有 aiocqhttp 系的 OneBot 实现提供 `set_group_card`）、
私聊没有群名片、机器人不是群管理/群主被协议端拒绝、或者还没收到过这个群的消息（拿不到机器人句柄）。
想手动接管可以用 `/vw nickname lock`，手动指定用 `/vw nickname set <文本>`。

**为什么不用向量检索记忆？** 记忆始终绑定在「会话 + 人格 + 地点 + 人」上，
召回范围很小且过滤维度是结构化的，SQL 更精确也更省开销。
